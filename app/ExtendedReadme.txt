PRODUCT LEARNING API - EXTENDED GUIDE
====================================

1. PROJECT OVERVIEW
-------------------
This project is a synchronous FastAPI application for managing products. It
uses:

- FastAPI for HTTP routes, dependency injection, and OpenAPI documentation.
- Pydantic v2 schemas for validating request bodies and response data.
- SQLAlchemy ORM for database models and queries.
- PostgreSQL through the psycopg 3 driver.

The API router is mounted below /api/v1. The product table is named
products_2. The application attempts to create the table when it starts.


2. INITIALIZE AND RUN
---------------------
Prerequisites:
- Python 3.10 or newer (the code uses PEP 604 union syntax such as str | None).
- A running PostgreSQL server and a database created for this application.

From the project root in PowerShell:

    py -m venv .venv
    .venv\Scripts\Activate.ps1
    python -m pip install fastapi "uvicorn[standard]" sqlalchemy pydantic pydantic-settings "psycopg[binary]"

Create or update app/.env. The settings module loads this path:

    APP_NAME=Product Learning API
    DATABASE_URL=postgresql+psycopg://username:password@localhost:5432/x_product_learning_db_3
    FRONTEND_ORIGIN=http://localhost:5174

Replace username, password, host, port, and database name with values for your
PostgreSQL installation. The database itself must exist before the application
starts. Keep real credentials private; do not commit them.

Start the server from the project root:

    python -m uvicorn app.main:app --reload

Useful URLs:
- Interactive Swagger UI: http://127.0.0.1:8000/docs
- ReDoc: http://127.0.0.1:8000/redoc
- Health check: http://127.0.0.1:8000/
- Ping: http://127.0.0.1:8000/ping

The startup code creates SQLAlchemy metadata in a background thread. This is
convenient for learning, but it is not a database migration system. For a
production application, use migrations and ensure database initialization
finishes before serving requests.


3. LAYERED REQUEST FLOW
-----------------------
For a product request, the general call flow is:

    HTTP request
      -> FastAPI controller (route and input validation)
      -> get_product_service dependency
      -> ProductService (transaction commit or rollback)
      -> ProductRepo (SQLAlchemy operations)
      -> PostgreSQL
      -> SQLAlchemy Product object(s)
      -> ProductRead response validation/serialization
      -> JSON HTTP response

The database session is created by get_db and closed after the request.
The dependency constructs a repository and service using that same session.
The service commits successful operations and rolls back when an exception
occurs. The repository builds or queries Product ORM objects. FastAPI uses the
route's response_model to validate and serialize those objects as JSON.


4. PRODUCT DATA AND VALIDATION
------------------------------
ProductCreate accepts these fields:

- name: required string, 3 to 20 characters.
- description: optional/nullable string, up to 200 characters; if present,
  the schema requires at least 1 character.
- price: required number greater than 0 and less than 10000.
- stock_quantity: required integer from 0 through 1000.
- is_active: boolean, default true.

ProductRead includes the ProductCreate fields plus id, created_at, and
updated_at. The ID and timestamps are generated by the database/model defaults.
All responses use JSON.


5. SIX CRUD OPERATIONS
----------------------
The examples below assume the server is running at http://127.0.0.1:8000.
They can be entered in Swagger UI or sent by an HTTP client.

5.1 Create a product
--------------------
Request:

    POST /api/v1/products
    Content-Type: application/json

    {
      "name": "Desk lamp",
      "description": "Adjustable LED lamp",
      "price": 39.99,
      "stock_quantity": 25,
      "is_active": true
    }

Expected: 201 Created and a JSON ProductRead object containing the submitted
fields plus generated id and timestamps.

5.2 List all products
---------------------
Request:

    GET /api/v1/products

Expected: 200 OK and a JSON array of ProductRead objects. An empty database
returns an empty array.

5.3 Read one product
--------------------
Request:

    GET /api/v1/products/1

Expected: 200 OK and one ProductRead JSON object when that ID exists. The route
constrains product_id to an integer greater than 0 and no greater than 1000.
The service/repository currently returns None for a missing ID; an explicit
404 response is not currently implemented.

5.4 Replace a product (PUT)
---------------------------
PUT supplies a complete ProductCreate body and replaces the product's editable
fields. Send every required field:

    PUT /api/v1/products/1
    Content-Type: application/json

    {
      "name": "Desk lamp - revised",
      "description": "Dimmable adjustable LED lamp",
      "price": 34.99,
      "stock_quantity": 18,
      "is_active": true
    }

Expected: 200 OK and the updated ProductRead object. The ID and timestamps are
not fields in the request body.

5.5 Update selected fields (PATCH)
----------------------------------
PATCH accepts ProductUpdate and is intended for partial updates. Only include
the fields to change:

    PATCH /api/v1/products/1
    Content-Type: application/json

    {
      "price": 32.50,
      "stock_quantity": 20
    }

The repository uses model_dump(exclude_unset=True), so omitted fields are not
overwritten. An explicitly supplied null is still a supplied value; only use
null for fields that are nullable in the database. Expected: 200 OK and the
updated ProductRead object.

5.6 Delete a product
--------------------
Request:

    DELETE /api/v1/products/1

Expected: 204 No Content with an empty response body. The current delete
repository method returns None if the ID does not exist, but the controller
still declares 204; explicit missing-record handling is not currently present.


6. FILTER PRODUCTS
------------------
Filtering is an additional endpoint beyond the six CRUD operations:

    GET /api/v1/products/filter?name_seq=lamp&min_price=10&max_price=100&active_status=true&sort_by=price&page_size=8&page_no=1

Supported query parameters:
- name_seq: case-insensitive substring of the product name (3-20 characters).
- description_seq: case-insensitive substring of the description (3-200 chars).
- min_price / max_price: price bounds; defaults are 1 and 9999.
- active_status: true or false; omitted means no active-state filter.
- created_after: timestamp; products created later than this value are selected.
- sort_by: id, name, price, stock_quantity, created_at, or updated_at;
  default is id.
- page_size: 5-20; default is 8.
- page_no: 1-2000; default is 1.

Example timestamp format:

    created_after=2026-01-01T00:00:00Z

The current filter route returns a JSON array of products. Pagination is
page-number based at the controller boundary. The repository applies filters,
sort order, offset, and limit. If no rows match, the result is an empty array.


7. HTTP STATUS AND VALIDATION NOTES
-----------------------------------
- Invalid body fields or query/path values are rejected by FastAPI/Pydantic,
  normally with 422 Unprocessable Entity.
- A successful create returns 201 Created.
- Successful reads and updates return 200 OK.
- Successful delete returns 204 No Content.
- Request/response property names are snake_case, such as stock_quantity.
- Keep the static /filter route registered before /{product_id}; otherwise
  FastAPI may interpret "filter" as the product_id path value.
